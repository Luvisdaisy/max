## MODIFIED Requirements

### Requirement: 显式启动的固定规模自动评测

系统 SHALL 提供 `max --benchmark` 入口，启动仅绑定回环地址的评测首页。首页 MUST 显示分别启动 10 条
和 100 条任务的入口；只有用户点击其中一个入口后，系统才可使用当前 `.env` 模型配置启动浏览器并顺序
执行对应的固定任务批次。页面 MUST 显示所选总进度、当前任务和终态报告路径。

#### Scenario: 点击 100 条入口后运行全量任务集

- **WHEN** 用户以 `max --benchmark` 启动评测首页并点击「运行 100 条」
- **THEN** 系统重置并依次执行完整 100 条任务，页面显示 `0/100` 至 `100/100` 的进度，全部结束后写入报告

#### Scenario: 10 条入口运行稳定子集

- **WHEN** 用户从首页点击「运行 10 条」
- **THEN** 系统仅执行完整版本化任务集中按原始顺序分层选出的 4 easy、3 medium、3 hard 任务，并沿用相同的重置、浏览器、Agent、评分与终止条件

### Requirement: 可审计原子指标报告

评测运行器 SHALL 为每个任务输出 JSON 结果，并为整次评测输出 JSON 和 Markdown 汇总。结果 MUST
包含任务标识、任务集版本、模型标识、严格成功、断言进度、终止原因、执行时间、工具调用数、工具
失败数、无效动作数、违规记录和已知 Token 用量；未知 Token 用量 MUST 保留为 `null`。汇总 MUST
包含请求执行的任务数量、实际结果数和可计量任务数，并分别报告任务成功率、部分完成率、平均执行
时间、平均工具调用数、工具失败率、无效动作率、违规率和已知 Token 用量，MUST NOT 以不透明综合
分替代这些指标。不同请求数量的报告 MUST NOT 被标记为同一全量实验结果，且 10 条与 100 条报告
MUST 写入不同文件。

#### Scenario: 已知与未知 Token 用量并存

- **WHEN** 一次评测中部分运行日志含 Token 用量、部分运行日志不含该字段
- **THEN** 单题未知值为 `null`，汇总只基于已知值报告 Token 用量，并标明已知样本数与请求任务数量

#### Scenario: 冒烟报告不覆盖全量报告

- **WHEN** 用户先后完成 10 条和 100 条评测
- **THEN** 两份报告分别标记请求任务数，并保存到不同路径，任一报告不会被另一批次覆盖
