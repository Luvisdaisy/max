## Context

当前交互边界由 `dispatch_input()`、`OperationResult` 和一个延迟创建的 Textual 应用组成。`OperationResult.messages` 只能表达无类型字符串，前端通过 `result.kind` 和跳过首条聊天消息等约定推断展示方式；模型工作在线程 worker 中执行，但输入未锁定，`exclusive=True` 可能让后一次提交取代仍在运行的请求。只读工具解释器已经返回工具名和压缩回执，但聊天入口只取最终文本，因此前端既无法区分工具活动，也不能安全地呈现阶段进度。

实现必须继续使用现有 Textual 依赖与 `src/` 布局，不增加联网或桌面输入能力。原始截图仅能停留在内存工具循环中；任何面向 UI 的事件都必须在业务边界完成净化。行为契约见 `specs/chat-console-ui/spec.md`。

## Goals / Non-Goals

**Goals:**

- 建立足够小且前端无关的结构化会话事件协议，消除前端对字符串位置和内容的推断。
- 让耗时模型调用、工具摘要和命令结果按确定顺序进入 Textual UI，并可靠维护忙碌、焦点与滚动状态。
- 使用现有 Textual 组件构建可测试的语义化消息、Markdown 回复、多行编辑区和命令菜单。
- 保证工具展示事件只能携带经过允许的工具名、状态和耗时。

**Non-Goals:**

- 不实现 token 级流式生成、运行中取消底层 `transformers.generate()` 或请求队列。
- 不为终端主题建立插件系统，也不追求复刻 Codex CLI 或 Claude Code 的品牌视觉。
- 不持久化聊天记录、输入历史或 UI 偏好。
- 不将 UI 展示事件升级为通用 Agent 编排事件总线；Agent 编排器仍是任务状态的唯一核心。

## Decisions

### 1. 以封闭的展示事件替代无类型消息元组

在 `console_core` 中增加不可变的 `ConsoleEvent`，字段限定为事件类别、显示文本以及可选的安全状态和耗时；事件类别使用项目内固定集合，例如 `assistant`、`command`、`tool`、`error` 和 `notice`。`OperationResult` 改为携带有序事件，并继续保留 `kind`、退出语义和退出码。

普通用户消息由前端在提交成功时立即渲染，dispatch 只返回后续结果，删除当前“聊天结果第一条等于原始输入、前端再跳过第一条”的隐式协议。工具事件构造函数只接受工具名、状态和耗时，不接受任意 `dict`，从类型边界阻止截图、参数或回执误入 UI。

备选方案是保留 `messages` 并在前端依据 `kind` 着色。该方案改动较少，但无法安全表达工具状态、Markdown角色和错误类别，且会继续依赖位置约定，因此不采用。

### 2. 使用短生命周期进度回调连接 worker 与 UI

交互 dispatch 接受一个可选的 `emit(ConsoleEvent)` 回调。模型加载、生成与只读工具执行只发布固定的净化进度事件；最终 `OperationResult` 仍作为单次调用的确定结果返回。Textual worker 收到进度后通过 `call_from_thread` 切回 UI 线程，所有 widget 更新都只发生在 UI 线程。

前端以单一 `busy` 标志在启动 worker 前完成互斥检查，忙碌期间禁用提交。worker 不再依赖 `exclusive=True` 取消前一个线程，因为 Python 线程中的模型生成不能被安全强制终止；完成路径使用 `finally` 统一停止计时器、恢复编辑区和焦点。每次请求携带递增 turn id，迟到回调只有在 id 匹配当前活动请求时才可更新活动状态。

备选方案是引入异步队列或让用户取消底层生成。这会要求改变生成器接口并处理 CUDA 推理中断与历史一致性，超出本次可用性变更范围。

### 3. 运行时只暴露必要的会话控制和状态转换

`LocalChatRuntime` 增加显式的 `clear_history()`，仅清空当前历史，不卸载模型或改变选择。`reply()` 通过可选状态通知报告 `loading`、`generating`、`ready` 或 `failed`；无论是否使用回调，现有成功后才写入历史的原子性保持不变。

`/status` 从运行时读取当前模型和状态，并由聊天入口提供固定的“本地、只读工具、无桌面输入、无网络”边界文本。`/clear` 先调用 `clear_history()`，再返回 `kind=clear`，由前端清空 transcript 并重新挂载欢迎状态。命令清单集中定义在 `console_core`，dispatch、`/help` 和命令菜单复用同一来源，避免文案与真实支持范围漂移。

备选方案是让 Textual 前端直接持有并操作 `LocalChatRuntime`。这会破坏现有 UI/业务分离并使命令单元测试依赖 Textual，因此不采用。

### 4. 使用语义化消息 widget 和受控 Markdown 渲染

会话区域继续使用可滚动容器，但不同事件挂载不同语义 widget：用户文本按纯文本渲染，MAX 最终回复使用 Textual `Markdown`，命令、工具、提示和错误使用禁用 Rich markup 的文本 widget。模型生成内容不得作为 Rich markup 或 TCSS 解释，链接不自动打开外部程序。

每个消息 widget 使用稳定 CSS class 表达角色和状态，颜色不是唯一差异，同时保留标签或符号。应用使用自定义紧凑顶部状态栏和底部快捷键栏，不再依赖占据较多空间且信息有限的通用 Header。终端 resize 时切换 `compact` class，由 TCSS 隐藏次要状态文本并保持主要状态、消息和编辑区。

预期结构：

```text
┌ MAX ─ 当前模型 ─ 本地/只读 ─ 运行状态 ┐
│ 会话记录                              │
│  用户纯文本                           │
│  工具净化状态                         │
│  MAX Markdown 回复                    │
│  新内容提示（仅回看历史时显示）       │
├ 命令筛选菜单（按需显示）──────────────┤
│ 多行编辑区                            │
└ 发送/换行/历史/帮助快捷键─────────────┘
```

备选方案是使用单一 `RichLog`。它适合高吞吐日志，但不利于每条消息的 Markdown、角色样式、测试选择器和后续状态更新，因此不采用。

### 5. 编辑器按键由一个入口统一仲裁

以 Textual `TextArea` 作为编辑器，并在应用级按键处理入口中按以下优先级仲裁：可见命令菜单、发送/换行、输入历史、常规编辑。`Enter` 提交，`Shift+Enter` 交给编辑器插入换行；历史使用明确显示在快捷键栏中的 `Ctrl+Up` / `Ctrl+Down`，避免与多行光标移动冲突。

当编辑内容以 `/` 开头且尚未包含换行时，菜单按照集中命令清单过滤；选择项只补全命令，不直接执行。普通文本和斜杠命令均在成功提交后写入仅驻留内存的输入历史。

备选方案是继续使用单行 `Input`，无法满足长任务描述和代码片段输入，因此不采用。

### 6. 显式管理自动滚动与新内容提示

挂载内容前记录滚动容器是否接近底部。位于底部时，在下一次布局完成后调用无动画滚动到底部；否则保持原 scroll offset 并显示新内容提示。提供一个底部快捷键将视口移到最新内容并隐藏提示。该逻辑集中在单一追加事件方法中，避免不同消息类型产生不同滚动行为。

测试不依赖像素颜色，而验证 widget 类型、CSS class、可见状态、焦点、dispatch 调用次数、滚动意图和敏感数据未进入 DOM。耗时只断言为非负且随计时推进，不断言精确毫秒。

### 7. 将工具失败建模为一次性受控观察，而非对话终点

只读工具循环仍然最多尝试一个工具。工具选择结构无效、工具未授权、参数校验失败或工具执行失败时，业务层不再直接抛出终止本轮的 `RuntimeError`，而是构造仅含可选工具名、稳定错误分类和安全摘要的失败观察，并调用最终解释阶段。最终解释阶段必须同时接收原始用户消息与该失败观察，使模型能够说明工具为何未能提供帮助，并继续回答用户原本的话语。

失败观察不得包含工具参数、原始回执、截图、异常堆栈或模型选择提示。一次失败后不得重试同一工具、选择第二个工具或进入递归工具循环；只有生成最终回复本身失败时，才由现有本地运行时错误路径终止本轮。工具状态事件仍可显示 `running` 与 `failed`，但 `failed` 只描述工具尝试，不代表整轮对话已经结束。

备选方案是把无效工具选择静默当作“无需工具”。该方案能恢复问候，却无法让 Agent 理解刚才发生的失败，也无法在最终回复中向用户准确说明受限能力，因此不采用。

## Risks / Trade-offs

- [每条消息独立 widget 在超长会话中增加布局开销] → 本次会话不持久化且本地模型上下文有限；先保持语义化实现，并用包含大量短消息的 Textual 测试监测明显退化。
- [线程进度回调与最终结果可能交错] → 所有 UI 写入切回 UI 线程，并使用 turn id 丢弃迟到事件；最终恢复逻辑只执行一次。
- [Markdown 内容可能包含终端控制样式或外部链接] → 只通过 Textual Markdown 文本接口渲染，不启用 Rich markup，不自动打开链接或执行内容。
- [工具摘要意外泄漏截图或参数] → 展示事件使用字段白名单，不接受任意元数据；增加包含敏感假数据的回归测试，确认 DOM 和结果事件均不含该数据。
- [模型可能过度强调与用户目标无关的工具失败] → 最终提示要求先完成原始用户意图，并只在有助于理解能力边界时简要说明净化后的失败；每轮仍限制一次工具尝试。
- [禁用编辑区会阻止用户提前编写下一条消息] → 本次明确选择单活动、无队列的可靠模型；排队与可取消生成留待具备运行时中断协议后的独立变更。
- [Windows 终端对 `Shift+Enter` 或组合键的编码存在差异] → 以 Textual 规范化 key event 为准，并在项目支持的 Windows 终端与 `run_test()` 中验证；快捷键栏提供可发现说明。

## Migration Plan

1. 先引入结构化事件、集中命令清单和新的运行时会话控制，并用不依赖 Textual 的单元测试固定协议。
2. 调整交互 dispatch 与只读工具解释流程，使其只发布净化事件，再将 Textual 前端整体迁移到新协议，避免同时维护两套消息格式。
3. 完成 Textual 交互、布局和敏感数据回归测试后，运行全量测试、依赖检查与实际命令验证。
4. 同步 `README.md` 和 `tech-design.md` 的当前已实现基线。

该变更没有持久数据迁移。若需要回滚，应整体回退事件协议、dispatch 和前端提交，恢复原 `OperationResult.messages` 契约；不得只回退前端而保留不兼容的核心结果类型。
