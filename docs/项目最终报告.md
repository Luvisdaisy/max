# 基于多模态大模型的桌面 GUI 智能体开发与优化：项目最终报告

> 报告日期：2026-08-30  
> 项目定位：面向本地桌面任务的多模态 ReAct GUI Agent 原型  
> 说明：本报告以仓库现状、已归档 OpenSpec、保留的运行产物和 Windows 侧 LoRA 完成记录为准。代码测试、真实任务评测和模型训练结果必须分别理解，不能相互替代。

## 1. 项目概述

本项目实现了一个通过屏幕截图理解界面、由大模型规划并调用键鼠工具完成桌面任务的 GUI Agent 原型。系统采用“用户指令 → 屏幕感知 → 任务规划 → 工具执行 → 后置观察与核验”的闭环，而不是将截图、OCR 或键鼠脚本作为彼此独立的功能。

当前仓库的核心技术组合包括 Python 3.12、Textual、LangGraph、Pydantic、HTTPX、PyAutoGUI、FastAPI、Vue/Vite、PyTorch、Transformers 与 PEFT。模型推理可通过 Ollama、ModelScope、DashScope、OpenRouter 与七牛等 OpenAI 兼容后端接入。

## 2. 系统设计与已实现能力

```text
用户指令
  ↓
Textual CLI
  ↓
LangGraph ReAct Agent（Think → Act → Observe）
  ├── 推理后端：统一流式 Chat Completions 与工具调用
  ├── 桌面能力：截图、移鼠、点击、拖拽、滚动、输入、按键
  ├── 感知能力：OCR、OmniParser UI 识别、macOS 辅助功能观察
  ├── 安全约束：观察前限制输入、移鼠后截图核验、敏感动作确认
  └── 可观测性：会话、运行事件、截图、Token 与终态记录
```

### 2.1 感知、定位与控制

- 支持全屏和区域截图，并保存模型视图像素与系统逻辑像素的映射，降低 Retina 缩放导致的误点风险。
- 支持鼠标移动、点击、拖拽、滚动、文本输入与组合按键；`keyboard_press` 使用严格的非空字符串数组契约。
- 支持整图 OCR、OCR 文本定位和 OmniParser UI 元素识别；旧截图或叠加图仅作观察，不可直接作为可执行定位依据。
- 点击或拖拽前要求先移动鼠标，并通过带红色光标的后置截图核验位置；界面变化后会清除过期定位结果。

### 2.2 Agent 闭环与可靠性

- 已实现 LangGraph 驱动的 Think → Act → Observe 循环，以及最大轮数、中断、会话恢复和任务上下文管理。
- 每轮根据当前任务、界面状态、子目标、近期动作与上轮结果生成单步动作；工具返回的成功不等同于任务完成。
- 已加入请求重试、上下文预算、运行状态层、任务完成证据核验与 Token 可观测性，便于复盘超时、截断或工具异常。
- 运行记录保存在 `artifacts/runs/`，会话与截图可用于定位失败，但其中产物默认不纳入 Git。

LoRA 微调已在 Windows 的 WSL 环境完成，采用 Qwen3.5-4B 的 4-bit QLoRA 路线，使用处理后的 ScreenAgent 数据。已记录的训练事实如下：

- 训练完成 3 个 epoch、`1500/1500` steps，验证集为 639 条样本。
- 训练结束指标：`train_loss=0.229`、`eval_loss=0.2432`。
- 已生成 adapter，并合并到 Windows/WSL 侧的 `qwen3.5-4b-lora` 模型目录；未覆盖基础模型。
- macOS MPS 在该 4B 多模态训练任务上出现显存不足且训练速度不适合，因此 Windows NVIDIA 环境是合理训练宿主。

上述训练记录证明训练和权重合并已完成；现有运行产物中没有基础模型与 LoRA 的同条件任务对比，也没有当前 macOS Agent 调用该模型的有效记录。当前主分支已不保留 `train_lora.py`、`eval_lora.py` 和旧 `remote` provider；模型权重与本地运行产物也被 `.gitignore` 排除。

## 4. 评测与验证现状

本项目已实现两类评测基础设施。第一类是本地 Web GUI 评测场，包含明确列出的 100 条任务和跨难度的固定 10 条冒烟集；运行器为每题隔离浏览器 profile、固定窗口条件、重置业务状态，并以隐藏状态断言进行严格评分。第二类是 Online-Mind2Web 评测，支持安全任务加载、隔离浏览器、轨迹导出、本地 v2 校验与可选 WebJudge 调用。

报告会分开统计任务成功率、部分完成率、耗时、工具调用、工具失败、违规、环境错误和已知 Token；未知 Token 不按零处理。真实网站评测只接受用户明确提供并授权使用的任务、安全清单与凭据。

评测部分尚未圆满完成。当前本地运行的小模型在多步骤 GUI 任务上的能力较弱，导致任务完成率过低；线上模型能够完成部分任务，但受调用次数、成本和可用额度限制，无法承担大规模批量测试。因此，现有评测系统已能运行和产出结构化报告，但尚未形成覆盖充分、具有统计代表性的模型能力结论。

## 5. 技术特点与项目价值

1. **闭环而非脚本拼接**：截图、模型推理和键鼠操作被组织为连续的观察—决策—执行—再观察流程。
2. **坐标安全优先**：显式处理图像缩放、逻辑像素、过期定位和点击前核验，降低 GUI Agent 常见的误点风险。
3. **评测口径清晰**：严格区分代码测试、模型任务成功率、环境失败和安全阻断，避免用单测数量替代 Agent 能力。
4. **训练与运行跨主机分工**：将高显存 LoRA 训练放在 Windows NVIDIA 环境，将 macOS 保持为桌面控制客户端，符合硬件约束。
5. **真实网页安全边界**：Online-Mind2Web 不下载任务、不使用个人账号、不绕过 CAPTCHA，并将高后果动作隔离在显式许可之外。

## 6. 项目难点与思考

### 6.1 难点不只是视觉能力，而是任务定义过重

GUI Agent 最初容易落入“截图 → 模型生成坐标 → 键鼠执行”的纯视觉坐标模式。在这一模式中，单个模型同时承担视觉识别、UI 语义理解、任务规划、目标定位和像素级坐标预测。任一环节产生小误差，最终点击都会失败；对于小尺寸图标、无文字按钮、Retina 缩放、截图压缩和多坐标系转换，这种误差会被进一步放大。

项目中已经针对这一问题实现了视图像素到逻辑像素的映射、定位结果时效控制、移动后的红色光标截图核验，以及 OCR 和 OmniParser 等感知补充。但实践表明，坐标换算正确只能避免“算对位置却点错屏幕”，不能解决模型本身对图标语义和目标位置的猜测问题。

### 6.2 将“想做什么”与“具体点哪里”分离

更合理的 GUI Agent 边界应为：模型负责表达语义意图，例如“点击发送按钮”或“在搜索框中输入文本”；UI grounding 层将该意图匹配到当前界面的元素；工具层再依据元素边界框或原生接口执行动作。即：

```text
LLM 规划
  ↓ 语义动作
UI Grounding
  ↓ element_id
受控工具层
  ↓ 坐标或原生 AX 动作
操作系统 / 浏览器
```

本项目已朝这一方向实现 macOS AX 结构化 UI 快照、短期 `element_id` 与 `ui_version` 约束，以及基于当前快照的语义点击和输入工具；坐标工具保留为视觉后备。这一设计避免模型直接暴露 locator、后端细节和任意坐标，也能在界面变化后拒绝使用过期元素。

不过，浏览器 DOM/辅助功能树和 macOS AX 树并不总是完整可用：Canvas、自绘控件、Electron/WebView 和缺失标签的图标仍需依赖视觉理解。因此更合适的原则不是完全弃用视觉，而是“结构化 UI 优先、视觉补充、坐标作为最终执行层”。当结构化信息不足时，截图、局部区域放大和带编号标记的可点击元素能降低纯坐标猜测带来的不确定性。

### 6.3 不确定时观察，不以猜测代替行动

多步 Agent 的另一难点是提示和循环策略容易隐含“每轮必须做一个操作”。这会让模型在无法可靠识别目标时仍然点击，表现为猜图标、猜快捷键或猜坐标。本项目通过观察前的输入限制、点击前移鼠核验、动作后的后置截图和任务完成证据检查，降低了盲目执行的风险。

更深层的认识是：重新截图、查询结构化 UI、查看局部区域、等待界面稳定，都应被视为正常决策，而不是失败或空转。GUI Agent 的可靠性不仅取决于能否采取动作，也取决于能否在目标不明确时拒绝采取高风险动作。

### 6.4 评测应定位失败层级，而不只统计最终成功率

当前本地 Web 评测能够输出任务成功率、工具调用、终态和时间等结果，但 0/10 的结果本身无法回答失败来自规划、元素识别、grounding、动作选择，还是执行后状态验证。单一端到端成功率适合呈现总体结果，却不足以指导模型或工具层迭代。

从本项目的经验看，评测应至少区分以下层次：

| 层次 | 需要回答的问题 | 适合的指标 |
| --- | --- | --- |
| UI 感知 | 关键可交互元素是否被看见并正确描述 | 交互元素召回率、角色/名称准确率 |
| Grounding | 指令目标是否对应正确元素 | Top-1 准确率、可点击命中率 |
| 动作 | 是否选择了正确动作及参数 | 动作准确率、无效动作率 |
| 轨迹 | 每一步是否合理、是否出现盲目重试 | 步骤成功率、重试率、错误点击率 |
| 任务 | 最终状态是否满足目标 | 严格任务成功率、完成时间、动作效率 |

其中，Grounding 是最关键的中间层。对 GUI 来说，坐标点是否落在目标元素的可点击边界内，通常比与元素中心点相距多少像素更有意义。对于目标不存在、标签缺失或图标相似的场景，还应记录模型是否选择重新观察，而不是执行幻觉式点击。

### 6.5 端到端成功率会放大底层误差

多步桌面任务对单步正确率非常敏感。若一个十步任务中每步正确率为 90%，理论上的完整成功概率约为 `0.9^10 = 34.9%`；单步正确率提升至 98% 时，完整成功概率约为 `0.98^10 = 81.7%`。因此，本地小模型在定位、动作格式或状态判断上的少量误差，会在长任务中迅速放大为低任务完成率。

这也是本项目评测结果偏低不能简单等同于“任务规划完全无效”的原因：端到端任务同时考验感知、grounding、动作执行、环境状态和模型推理。当前 LoRA 训练与评测尚未形成充分对比数据，无法据此量化模型在哪个环节获得提升。

### 6.6 模型能力、接口兼容性与评测成本相互制约

本地小模型虽然便于反复调用和保护隐私，但难以稳定处理复杂视觉语义与长轨迹任务；线上模型具有更高完成潜力，却受到调用配额、单次费用与批量评测成本的限制。另一方面，远程模型服务还需要兼容流式响应、工具 schema、图像输入、finish reason 和用量统计，接口链路的任何不兼容都会使评测在真正执行桌面动作之前中止。

因此，LoRA 微调和评测并非两个独立问题：只有在推理服务、工具调用协议、任务环境和评测口径均稳定的条件下，才可能将基础模型与 LoRA 模型放在同一条件下比较。当前项目已经完成训练和评测基础设施，但受时间、精力、模型能力与调用成本限制，尚未获得足以支撑有效性能结论的验证数据。

## 7. 最终结论

本项目已经完成桌面 GUI Agent 的主要工程与算法原型：多模态观察、ReAct 规划、桌面工具调用、坐标安全、运行可观测性、离线 Web 评测以及受控在线评测均已具备。Windows 侧 LoRA 微调已经完成，是项目的重要训练产出。

当前项目已具备完整的 GUI Agent 原型能力和相应的工程质量验证，但评测系统兼容性、本地小模型的任务能力，以及线上模型的调用次数和费用约束，共同限制了大规模有效测试。现有证据包括一次 10 题本地 Web 冒烟与一次 Online-Mind2Web 单题运行；二者均未产生任务成功记录。LoRA 微调已在 Windows/WSL 环境完成，但 LoRA 效果与评测结果均未经过充分的验证测试，尚不能得出有效的能力提升或性能结论。
