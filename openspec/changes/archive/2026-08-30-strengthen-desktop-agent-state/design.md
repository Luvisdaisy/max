## Context

现有 `TaskContext` 已包含用户指令、计划、当前子任务、最近观察、动作摘要、截图绑定事实、恢复信息和完成核验。它解决了“任务是否可恢复”和“完成是否有后置证据”，但对于“当前哪个应用／窗口接收输入”“是否进入文件选择器”等状态，模型只能从截图自行推断；计划推进也主要依赖模型文本标记，而不是观察到的结果。

本设计在现有 `think → act → observe` 图中加入轻量状态快照和逐动作预期。所有状态仍以最新观察帧为准，且必须与现有坐标换算、移鼠后截图和独立完成核验兼容。

## Goals / Non-Goals

**Goals:**

- 用一个可恢复、可脱敏的状态胶囊表达任务目标、进度、最新桌面观察、近期动作和待验证预期。
- 在 macOS 可用时以只读方式获取前台应用、窗口、焦点与对话框；不可用时明确为未知，不用视觉猜测伪造结构化值。
- 把当前帧上的语义定位／OCR 结果归一为有限 UI 候选，供模型理解和预期验证；候选只在来源帧有效。
- 将进度推进改为“后置观察满足预期”驱动，并将无法验证的状态交给恢复护栏处理。
- 保持旧会话和 checkpoint 可读，且不扩大敏感信息持久化范围。

**Non-Goals:**

- 不构建完整 Accessibility UI Tree、跨平台窗口管理器或通用 GUI 自动化框架。
- 不在本变更中引入 Accessibility API 直接聚焦、点击或输入；后续语义 UI 后端若引入此能力，仍不得绕过后置观察、进度和完成核验链路。
- 不保存完整 OCR／caption 正文、控件逻辑坐标、截图字节、键盘输入正文或长期记忆。
- 不把视觉差分或 LLM 判断单独当作副作用任务完成证据。

## Decisions

### 1. 引入“观察快照”，但不以它替代截图或 ViewFrame

在 `TaskContext` 增加 `desktop_snapshot`，由每次成功观察创建，包含 `frame_path`、时间戳、可选的 `active_app`、`active_window`、`focused_element`、`active_dialog` 与最多固定数量的 `ui_elements`。应用和窗口只保留稳定标识、短名称／标题、角色和可选边界摘要；UI 候选只含来源、语义标签、能力和短标识，不保存可执行坐标。

快照的 `frame_path` 必须等于当前活动 ViewFrame。一次新截图、桌面副作用后的后置截图或恢复到不同帧时，都必须替换快照并使旧 UI 候选、焦点和弹窗状态失效。这样保留 MVP 的“我现在在哪”信息，却不会把它变成跨帧输入授权。

选择单一快照而不是保留窗口树或多帧状态历史，是为了限制上下文与陈旧状态。原始截图仍是视觉事实来源，ViewFrame 仍是唯一坐标权威。

### 2. 前台身份采用只读分层采集与显式未知值

新增桌面观察适配器：优先读取主机的只读前台应用／窗口／焦点／对话框信息；若无权限、平台不支持或信息不完整，则分别记为 `unknown`，并记录机器可读的采集状态。视觉、OCR 或模型文本只能补充 UI 候选，不能冒充前台应用、窗口或焦点。

选择显式未知而不是从图像推断应用名称，是为了防止快捷键、文本输入被错误地归因到前台窗口。首版只使用采集结果丰富模型上下文；桌面工具的现有截图与动作门禁不依赖它，以免权限差异改变动作可用性。

### 3. 以受限 Expectation 驱动 ProgressItem

每一项进度包含稳定 ID、短描述和 `pending`／`in_progress`／`verified`／`blocked` 状态。模型在提出一个桌面副作用动作时可同时给出一种受限预期：`dialog_appears`、`active_window_changes`、`element_appears`、`element_disappears`、`element_selected` 或 `screen_changed`，并且预期只引用最新快照的非坐标语义标识。

`observe` 负责用动作前后快照、UI 候选及结构化采集结果计算预期结论。满足预期才推进关联进度项；证据不足时结果为 `unverified`，进度不前移，并把中文原因写入恢复信息。`task_complete` 继续使用其独立声明后观察机制，不被一般预期替代。

选择有限预期类型而不是任意布尔表达式，便于确定性验证、测试和小模型工具契约。模型仍可在无合适预期时不创建预期，系统不得凭“工具未报错”推进进度。

### 4. 统一状态摘要与持久化边界

模型上下文获得紧凑摘要：当前前台状态（或未知）、当前子任务及进度、最近动作结果、当前有效 UI 候选／短期事实和待验证预期。它不含坐标、完整标题／OCR 正文、历史帧候选或敏感输入。

`Session.task_context` 和 checkpoint 持久化同一份清洗后的状态；旧会话缺少字段时以空快照、空预期和现有计划恢复。序列化前统一截断大小、丢弃错误枚举和不匹配当前帧的 UI 候选。会话开始新用户任务时，保留既有只读对话观察规则，但不得继承上一任务的桌面快照、进度、预期或可执行事实。

## Risks / Trade-offs

- [辅助功能权限不足导致状态不完整] → 使用逐字段 `unknown` 与诊断码，保留截图／OCR 流程，不阻塞只读或既有桌面工具。
- [新快照被误认为坐标授权] → 快照不持久化可执行坐标；所有执行仍验证当前 ViewFrame 与既有移鼠／截图门禁。
- [过宽 UI 候选增加上下文和误匹配] → 固定上限、短标签、来源帧绑定，只有唯一可信语义结果进入候选。
- [视觉变化无法证明业务成功] → 通用 expectation 只能推进局部进度；任务完成仍需既有独立完成证据。
- [旧 JSON 损坏或格式漂移] → 采用宽容解析和安全降级，不阻断恢复。

## Migration Plan

1. 定义状态对象、清洗器与观察适配器的接口，先仅产出快照和上下文摘要。
2. 在 `observe` 接入状态更新、帧失效和有限 UI 候选；覆盖权限不足与新帧失效测试。
3. 加入 expectation／progress 验证器，并让图只在验证通过后推进进度。
4. 扩展会话／checkpoint 序列化和旧格式兼容测试。
5. 以 fake desktop、mock 观察适配器和真实 macOS 冒烟验证；回滚时忽略新增字段，现有计划、工具和完成核验仍可运行。

## Open Questions

- 首版是否把“活动窗口标题变化”作为 `active_window_changes` 的唯一可验证条件，还是允许应用 ID 变化也算成功？建议二者均可，但要求动作前后都有可信采集值。
- UI 候选的文本匹配是否允许内置中英文别名？建议首版只规范化空白与大小写，别名另行提案。
