## Context

参见 `proposal.md` 的动机。当前 CLI 在创建基准归档前只检查 `config.json`，随后由加载器和推理逻辑直接抛出异常；归档配置还包含绝对模型与图像路径。已有 `ExperimentArchive` 提供配置、环境、轨迹与结果文件，加载器使用 `local_files_only=True`，因此可以在不引入新依赖或网络访问的前提下收敛该流程。

## Goals / Non-Goals

**Goals:**

- 在模型加载前完成可单元测试的本地模型和图像预检。
- 使基准在归档创建后的任何失败阶段都留下结构化、非敏感的诊断证据。
- 将 CLI 输出、归档字段和文档中的验收方法保持一致。

**Non-Goals:**

- 不下载模型、不提交 `model/` 或 `artifacts/` 内容，也不在自动化测试中执行真实 GPU 推理。
- 不支持其他模型、量化格式、CPU 推理、多图批处理或网络回退。
- 不改变 Doctor 的无模型边界，也不实现桌面控制。

## Decisions

### 1. 预检采用确定性的本地文件与解码检查

基准入口将在创建归档后、加载模型前验证规范化后的目录严格等于仓库内 Qwen3.5-4B 目标，并检查推理所需的配置及权重/处理器文件；同时以 Pillow 仅验证图像可解码。这样能在占用 GPU 前给出具体错误，并把检验限制在本地 I/O。

备选方案是只依赖 Transformers 加载报错。它不能区分缺失文件、目录错误和远程回退风险，且无法稳定测试，因此不采用。

### 2. 基准编排器拥有阶段化失败归档

预检将作为 `run_benchmark` 的首个受保护阶段，统一写入 `benchmark_started`、阶段性失败事件和失败 `result.json`。结果使用稳定的阶段名称与面向用户的错误消息；原始异常仅在不含敏感路径时保留。这样不论失败发生在预检、加载或推理，归档结构保持一致。

备选方案是由 CLI 在归档器之外捕获错误。该方案会分散失败协议并遗漏未来调用方，因此不采用。

### 3. 归档使用非敏感、可复现的逻辑标识

配置记录固定模型标识、相对/逻辑输入标识、提示词、生成长度和 `offline: true`，不记录绝对路径、图像字节或模型清单。环境记录继续来自既有诊断输出。文档将说明开发者在本机将归档路径与命令关联，而不是把路径写入可共享证据。

备选方案是保存绝对路径以便直接复跑。它会泄露用户目录结构，且不利于跨机器复现，因此不采用。

## Risks / Trade-offs

- 模型文件布局随上游版本变化 → 预检只检查本项目锁定模型所需的最小文件集合，并由实际离线加载保留最终判定。
- 图像解码需要读取用户文件 → 仅在用户显式传入路径时读取，不复制或归档图像内容。
- 真实 4B 推理需要足够 GPU 资源 → 自动化测试仅使用注入的替身；实际验收命令由已准备环境的开发者执行。
- 错误文本可能含路径 → 归档前对错误信息进行路径净化，并在测试中断言不写入绝对路径。

## Migration Plan

1. 为模型目录、图像与归档载荷补充纯函数预检和路径净化测试。
2. 重构基准编排与 CLI，使归档先创建、所有后续阶段都经统一失败记录处理。
3. 更新 README 与技术报告的下载、离线基准和证据验收说明。
4. 执行单元测试、`pip check`、CLI 帮助和 OpenSpec 验证；在具备完整本地模型和 GPU 的交互环境中执行一次真实基准。
5. 如预检错误地拒绝受支持模型，回退该变更并保留原有离线加载路径，待确认上游布局后重新制定最小文件集合。
