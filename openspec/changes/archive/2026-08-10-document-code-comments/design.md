## Context

仓库已在 `AGENTS.md` 中规定新增或修改代码应具备完善的中文注释，但现有实现与测试的注释覆盖和表达方式不一致。详见 `proposal.md`。本次仅允许修改注释与说明文档，不得借机重构、格式化或调整代码行为。

## Goals / Non-Goals

**Goals:**

- 使每个 Python 模块的职责和对外使用方式可由中文说明快速识别。
- 使复杂控制流、数据转换、平台限制、异常处理及安全或性能取舍具有可追溯的中文解释。
- 使测试文件与非直观断言清楚表达其保护的回归场景。
- 在 `tech-design.md` 中记录已实现基线的注释维护要求。

**Non-Goals:**

- 不改变模块接口、运行行为、测试覆盖范围、依赖或配置。
- 不为语义自明的赋值、分支或循环添加机械逐行注释。
- 不把未实现的路线图描述为当前交付能力。

## Decisions

### 按模块职责和认知成本确定注释粒度

为实现模块添加中文模块文档字符串；为公开类、函数、命令入口和数据模型添加中文用途、参数或返回约束说明；仅在逻辑意图无法由代码直接推断时补充行内注释。相比对每一行代码注释，这种方式能覆盖设计意图且降低注释漂移风险。

### 按功能域分批审查源码与测试

实现阶段依次审查基础配置与运行时、模型下载与推理、诊断与命令行、编排器、感知工具、测试。每一批完成后核对改动是否仅限注释和文档。相比一次性机械处理所有文件，分批方式更便于发现跨模块术语不一致和缺失的边界说明。

### 用现有自动化验证行为未变，并进行人工注释审查

运行完整单元测试、依赖一致性检查和诊断命令，证明注释编辑没有影响行为；再根据本设计的覆盖准则人工审查差异。自动化测试无法判断注释是否准确或有价值，因此不能作为唯一验收方式。

### 更新技术设计报告的已实现基线说明

`tech-design.md` 仅补充当前实现的注释文档维护要求，并与实际代码及验证结果核对。相比新增独立的开发手册，这可以避免职责分散，同时保留报告中已有的路线图内容。

## Risks / Trade-offs

- [注释与代码脱节] → 在每个功能域完成后对照实现审查，并将同步更新注释写入维护要求。
- [注释过多降低可读性] → 仅注释模块边界、公开接口、复杂意图和非直观约束；删除重复代码字面的说明。
- [测试或诊断验证受环境影响] → 记录实际执行环境和失败原因；只在验证成功后标记对应任务完成。
- [全仓库修改遗漏文件] → 以已盘点的 `src/max_agent/` 与 `tests/` Python 文件清单为核对范围，并在最终差异审查时复查。

## Migration Plan

1. 依功能域补充源码与测试注释，并同步更新技术设计报告。
2. 审查差异，确认没有可执行逻辑、依赖或配置变更。
3. 运行项目规定的验证命令并记录结果。
4. 若发现行为变化或注释不准确，撤销对应实现改动并依据实际代码重写说明；本变更无需数据迁移或部署步骤。
