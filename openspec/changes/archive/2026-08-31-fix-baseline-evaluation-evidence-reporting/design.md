## Context

现有 `--baseline` 在任务 JSON 中同时设定 `max_actions` 与 60/90 秒超时，并用
`asyncio.wait_for()` 直接取消 `AgentRunner.run()`。直接取消会绕过 Agent 的终态持久化，导致超时题没有
运行摘要、运行 JSONL 或最终截图；而当前成功口径还要求 `task_complete`，因此即使最后画面已显示目标，也会失败。

2026-08-31 的实测记录还表明，执行模型连续调用后，独立评审立即触发 Qiniu RPM 429。评审函数把异常折为
`indeterminate`，最终报告没有区分“无法评审”与“截图判定任务失败”。现有批次目录还会输出 manifest、逐题 JSON、
summary、HTML 等多个记录文件，与用户要求的单一时间戳 JSON 不符。

## Goals / Non-Goals

**Goals:**

- 每题仅受 180 秒执行超时约束，不以动作数量中止，但保留防止危险或重复个人写入的行为护栏。
- 每题发送一张最终状态截图给独立评审，并用该结论作为成功判定依据；对无法评审、超时和执行错误保留可审计证据。
- 一次基线运行在指定目录只持久化一个时间戳 JSON；自动由 Python 脚本根据这个 JSON 生成图表与中文报告。
- 明确显示执行、评审、证据缺失与安全阻断的不同原因，并记录 Token、耗时、步长和重试信息。
- 让用户在终端直接核对 Agent 实际任务提示词、模型正文、逐步工具调用，以及评审 AI 的输入和原始输出。

**Non-Goals:**

- 不改变 Web `--benchmark`、不绕过 GUI 工具直接查询应用数据库或使用脚本完成任务。
- 不在评审失败后重放 Agent，亦不自动撤回提醒事项或微信消息。
- 不保证提供方在单次评审请求中永不返回限流；限流必须如实记录，不能伪造成任务失败或成功。
- 不打印模型 reasoning/思考增量，不打印完整 HTTP 请求、API Key、截图二进制或 base64，也不扩大单一运行 JSON 的持久化字段。

## Decisions

### 1. 以执行超时替代动作预算，并保留任务专属安全规则

任务定义删除 `max_actions` 字段，所有任务 `timeout_seconds` 固定为 180。护栏不再累计并拒绝普通鼠标和键盘
动作；仍拒绝 Terminal 非 `whoami`、WeChat 导航或非指定文本、Reminders 非指定文本，并保留每轮一次个人写入。
这使复杂界面不会因固定步数被截断，又不扩大用户授权范围。替代方案是提高动作上限；不采用，因为它仍会在
未知复杂度下形成隐性失败阈值。

### 2. 采用“温和中断 + 终态快照”保留超时证据

编排器以独立任务运行 Agent。达到 180 秒时先请求 `runner.interrupt()`，在短暂收尾窗口等待其写出终态；仅当
收尾窗口也耗尽时才取消协程。无论正常、异常、超时或被迫取消，编排器都调用只读 screenshot 工具获取一张当前
桌面快照，并注明来源为 `post_termination_snapshot`。这张快照和可用会话/运行摘要构成评审输入和人工复核证据。

替代方案是仅读取 Agent 最后一张工具截图；不采用，因为直接取消时该状态可能未返回，且最终显示状态可能发生在
最后一次工具截图之后。

### 3. 独立评审一次请求、独立状态与可解释成功公式

评审使用全新、无工具的客户端，只输入任务 rubric、运行日期和一张终态截图。评审客户端最多总尝试三次；仅在
尚未产生流式输出的可重试错误时按指数退避重试，并在每次尝试中复用同一张截图。调度器在执行模型最后一次请求后
预留可配置的冷却时间，避免同一 RPM 窗口内立即触发 429。评审得到 `pass`、`fail`、`indeterminate` 或
`review_error`，后两者与执行错误分别记录。

最终成功公式为：未触发安全违规、存在终态截图且独立评审 verdict 为 `pass`。`agent_claimed_complete`、执行终态
及 `task_complete` 仅用于诊断。替代方案是继续要求完成声明；不采用，因为它会把已可见的完成状态误判为失败。

### 4. 单一运行 JSON 与目录外自动报告

完成一次基线运行后，`artifacts/evaluations/baseline-desktop/<timestamp>.json` 是该目录中唯一的新文件，不创建
批次子目录或逐题 JSON。该 JSON 内嵌 manifest、逐题记录、汇总、截图/运行日志引用、调用次数、重试、已知或
未知 Token、执行/评审/总耗时、步长和错误详情。

CLI 随后调用 `src/max_gui/baseline/report.py` 的公开脚本入口，从这个 JSON 读取数据并在
`artifacts/evaluations/baseline-desktop-reports/<timestamp>/` 写入图表 PNG、HTML 和 Markdown。报告目录放在
baseline 目录外，满足单一记录文件约束且保留图表产物。替代方案是把图表嵌入 JSON 或继续写 dashboard 到批次目录；
前者不可直接查看，后者违反结果文件布局。

### 5. 用专用控制台投影展示调用链，并从数据源排除思考过程

基线服务在构造 `task.render_prompt(nonce, run_date)` 后先以带任务/轮次标签的区块打印该字符串，再把同一字符串传给
`AgentRunner.run()`，从而保证“显示内容”和“实际发送内容”没有两套拼接逻辑。Agent 正文使用现有 `on_token`
回调流式输出；基线不传 `on_reasoning`，也不从包含 `reasoning` 的会话消息或评测步骤中读取该字段。

工具调用使用 `on_evaluation_step` 的执行后回调投影为递增步骤，打印工具名、解析后的参数、成功/失败、结果文本和截图
路径。投影器显式挑选允许字段，忽略回调载荷中的 `reasoning`；这样既能展示实际执行顺序与结果，也不会因直接 dump
载荷而泄露思考过程。模型正文为空而只返回工具调用时，仍打印工具步骤，不伪造模型正文。

独立评审由 `review_screenshot()` 在发送前回调结构化输入：provider、model、完整评审文本和截图路径；发送后回调原始
`delta.text`，解析失败时也先显示原始输出，再返回既有 `review_error`。终端只展示截图路径，不展示
`encode_user_content()` 产生的图像数据。评审错误使用现有安全摘要遮蔽常见密钥；所有区块即时 `flush`，但不写入
baseline 结果 JSON。

替代方案是读取会话消息和运行 JSONL 后统一打印；不采用，因为助手消息内同时保存正文与 reasoning，后处理时更容易
误输出思考内容，且无法实时观察工具执行与评审请求。

## Risks / Trade-offs

- [无动作预算会使低质量模型更频繁调用] → 180 秒硬超时、模型迭代限制、工具安全规则和每轮写入预算仍生效，并记录步长供比较。
- [温和中断仍可能无法收尾] → 收尾窗口后明确标记 `timeout_forced`，保留编排器的终态截图与可用事件摘要。
- [共享 provider 仍可能 429] → 评审最多三次指数退避并记录 request/error；配置冷却时间，必要时由用户配置不同评审 provider，绝不把它算为 `fail`。
- [截图可能包含私人信息] → 仅保存评测所需的一张证据截图，沿用现有 provider 风险提示，不持久化对话、推理或键盘输入正文。
- [工具参数与结果在当前终端可见] → 启动确认文案明确控制台可见范围；只在用户主动运行 baseline 的终端打印，不复制到
  单一结果 JSON，并继续使用安全错误摘要遮蔽常见凭据。
- [未来回调载荷新增 reasoning 字段后被误打印] → 控制台投影使用允许字段列表，不直接序列化回调对象，并用哨兵测试断言
  reasoning 内容不出现在捕获输出中。
- [报告与 JSON 写入中断] → 先原子写入 JSON，报告失败单独打印原因；JSON 仍是完整的可重跑输入。

## Migration Plan

1. 更新任务 schema、护栏、编排器、结果模型与 CLI；将旧目录式记录视为历史兼容输入。
2. 新增 fake Agent/评审测试，覆盖成功但未声明、超时后快照、单次评审、429、单 JSON、脚本报告和控制台调用链。
3. 运行 Ruff 与相关/完整 pytest；不把模拟结果称为真实桌面验证。
4. 用户重新启动一轮真实基线后，检查五条 JSON 记录、截图评审与报告图表；若 provider 限流仍出现，以记录的 request ID 和冷却时间调整为准。

## Open Questions

- 评审冷却时间的默认值将采用 60 秒，除非配置中已能获得 provider 的 RPM 或 `Retry-After`；该值需要在真实运行后根据实际 provider 限制校准。
