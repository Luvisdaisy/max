## Context

当前 Textual 聊天通过 `cli.py` 注入固定的 `LocalChatRuntime`，而运行时仅验证并加载仓库内的 Qwen3.5-2B 路径。`model/` 已按提供方和模型目录组织，不能把第一层提供方目录直接当成可加载模型。参见 `proposal.md` 的动机与本变更的 delta 规格。

## Goals / Non-Goals

**Goals:**

- 提供稳定、可显示的本地模型目录名，并允许会话期间通过 `/model` 查询和切换。
- 将模型选择、模型生命周期和输入分发保持在现有 CLI、核心分发、Textual 前端的分层内。
- 切换后隔离模型实例和聊天历史，保持仅本地、按需加载的运行边界。

**Non-Goals:**

- 不下载、删除、转换或联网发现模型。
- 不实现模型参数配置、并行多模型、跨会话持久化选择或自动模型兼容性适配。
- 不改变基准测试中针对固定 Qwen3.5-4B 的既有约束。

## Decisions

### 以包含 `config.json` 的后代目录发现模型

从仓库根目录的 `model/` 递归枚举包含 `config.json` 的目录，并以相对路径（例如 `Qwen/Qwen3.5-2B`）作为选择键和展示名。这样既支持现有提供方分层，也避免同名模型目录冲突。

备选方案是只枚举 `model/` 的一级目录；它会把 `Qwen`、`ZhipuAI` 等分类目录误认为模型，无法满足现有目录结构。

### 在 LocalChatRuntime 中维护选择与切换生命周期

运行时持有当前选择的相对目录和已加载资源。选择成功即丢弃已加载模型、处理器与历史；下一次 `reply` 懒加载新选择。加载或生成失败不会改变已选择名称，以便用户修复文件或改选其他模型。

备选方案是在前端直接重建运行时；这会把模型生命周期泄漏到 UI 层，也更难保证命令行与未来前端的一致行为。

### 在核心分发层解析 `/model`

`console_core` 接收一个模型处理回调，将 `/model` 和 `/model <目录>` 转换成统一 `OperationResult`；CLI 装配模型发现和选择回调；Textual 仅渲染结果。模型名称参数保留内部空格，首尾空白会被忽略。

备选方案是让 Textual 前端自行解析命令；这会使命令行为无法脱离 UI 单独测试。

### 以当前运行时默认模型维持首次使用体验

启动时保留现有 Qwen3.5-2B 路径为默认选择，但将其作为可验证的模型选择而非硬编码加载目标。若默认模型未被发现，普通聊天返回可诊断错误，用户仍可用 `/model` 选择其他本地模型。

## Risks / Trade-offs

- [不同目录的模型与现有 Transformers 多模态加载器不兼容] → 在推理时以明确本地加载错误报告，不提供远程或自动兼容回退。
- [切换模型会释放 Python 引用但 CUDA 显存回收可能延迟] → 切换时丢弃旧实例并在可用时清理 CUDA 缓存；不承诺即时显存归还。
- [递归发现可能包含不完整下载目录] → 清单仅表明可选择；加载前仍执行完整性验证并报告缺失文件。

## Migration Plan

1. 为模型发现、选择、切换和命令分发添加单元测试。
2. 将固定路径验证改为面向当前选择的验证，并保留默认选择。
3. 接入 CLI 和 Textual 渲染，更新技术设计报告。
4. 运行单元测试、格式检查、依赖检查和 OpenSpec 严格校验；若回退，恢复固定默认选择的运行时调用路径。
